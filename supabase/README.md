# Общий мир — план переделки

Цель: настоящий общий мир на несколько живых игроков (как в RoK), где события
(постройка, сбор, бой, приход похода) разрешаются сервером сами по себе, даже
если ни один игрок сейчас не в игре. Делается поэтапно — на каждом шаге игра
остаётся рабочей, однопользовательский режим не ломается.

## Почему так

Сайт — статика на Render (`render.yaml`), собственного постоянно работающего
процесса завести негде. Значит бэкенд — это Supabase: Postgres как источник
правды + Edge Functions на каждое действие + `pg_cron`, который тикает сам по
расписанию и досчитывает события, независимо от того, открыт ли у кого-то
браузер.

## Фазы

1. **Фундамент (эта миграция, `0001_multiplayer_foundation.sql`)** — таблицы
   `worlds`/`players`/`map_cells`/`marches`/`events`/`mail` + RLS. Ничего в
   `index.html` ещё не меняется, существующий однопользовательский сейв
   (`saves`, по `device_id`) работает как раньше и не трогается.
2. **Сервер считает время** — `pg_cron` + Edge Function-тикер, который
   разбирает `events` по расписанию (аналог `EV{...}` в index.html, только на
   сервере). Проверяется на 1-2 действиях, не на всех сразу.
3. **Общая видимость** — все игроки читают одни и те же `players`/`map_cells`
   вместо приватных ботов у каждого в браузере; новый игрок попадает в тот же
   мир, не в свой собственный.
4. **PvP по-настоящему** — бой между живыми игроками считает сервер один раз,
   результат одинаков у обеих сторон.
5. **Полный перенос действий** — постройки/войска/академия/крафт и т.д. по
   одному переезжают на сервер (Edge Function на каждое), клиент становится
   тонким: жмёт кнопку → ждёт ответ сервера → рисует.

Расчётные формулы (стоимость построек, боя, сбора и т.д.) уже написаны как
чистые JS-функции в `index.html` — их предполагается не переписывать заново
на SQL, а вынести в общий модуль, который сможет использовать и браузер (для
мгновенного предпросмотра), и Edge Function (Deno, тот же JS/TS) — как
единственный источник правды по правилам игры.

## Фаза 8, кусочек 3 — респаун истощённых точек и разгромленных лагерей

Третий кусочек карты мира — закрывает честный пробел, оставленный в
кусочках 1 и 2 намеренно: раньше истощённая точка сбора просто оставалась
на карте пустой навсегда, а разгромленный лагерь исчезал без следа. Теперь
оба возрождаются рядом со старым местом — зеркало `mapDelete`+
`schedule(CFG.NODE_RESPAWN/CFG.RESPAWN_CAMP,...)` из index.html
(`EV.gathered`/`arriveMarch` camp-ветка, index.html:4993-4997/5151-5152).

**Что добавлено (только `mp-tick`, новых функций/миграций не нужно):**

1. **`applyGathered`** — если добытая точка опустела (`amount<=0`, уже
   списан в `mp-gather` на отправке), клетка сносится и заводится новое
   событие `type:"node_respawn"` через `NODE_RESPAWN_SEC=3600` (1ч, то же
   значение, что `CFG.NODE_RESPAWN`).
2. **`applyRaidArrive`** — на победе, СВЕРХ уже существующего сноса
   клетки, заводит `type:"camp_respawn"` через `CAMP_RESPAWN_SEC=2700`
   (45мин, то же, что `CFG.RESPAWN_CAMP`).
3. **Новые `applyNodeRespawn`/`applyCampRespawn`** — та же формула уровня/
   количества, что у `seedNodesAround`/`seedCampsAround` в `mp-join`
   (случайный уровень 1-3 для узла / 1-5 для лагеря, честное упрощение —
   не hash-плотность `nodeLevelAt`/`campRawAt`), место — небольшое случайное
   смещение (3-12 клеток) от СТАРОЙ позиции, не полноценный перебор чанка
   (`findFreeCellInChunk`). `upsert` с `ignoreDuplicates` — редкая коллизия
   координат просто пропускается, без падения тикера.

Клиентская панель не менялась — `mpRefreshNodes`/`mpRefreshCamps` уже
опрашивают `map_cells` напрямую, новые/снесённые клетки появляются в
списке сами по себе на следующем опросе (раз в 5с).

### Как применить

Передеплоить только **`mp-tick`** — остальные функции/SQL не менялись.

## Фаза 8, кусочек 2 — лагеря варваров (mp-raid)

Второй кусочек карты мира — прямое продолжение кусочка 1 (точки сбора):
тот же приём (seed вокруг новичка, отдельный Edge Function на действие,
разбор при прибытии в mp-tick), только вместо сбора — бой.

**Что добавлено:**

1. **`mp-join`** — `seedCampsAround` сеет кольцо из 3 лагерей (`map_cells`,
   `t:"camp"`) вокруг столицы нового игрока, уровень 1-5 (случайный, честное
   упрощение — не hash-плотность `campRawAt`, index.html:2974). Плотность
   узлы:лагеря = 5:3, тот же порядок, что 22:13 у одиночной игры
   (index.html:3156).
2. **Новая Edge Function `mp-raid`** — dispatch-only, тот же марш-конвейер,
   что у `mp-attack`/`mp-gather` (marchSlots — общий пул на все три режима
   теперь). Сам бой НЕ здесь — только отправка.
3. **`mp-tick`** — `applyMarchArrive` получил ветку `mode==="raid"`
   (`applyRaidArrive`). Бой — `resolveBanditRaid`, зеркало ветки camp/fort в
   `arriveMarch` (index.html:5133-5158), но той же ОДНООБМЕННОЙ моделью, что
   и PvP (`resolvePvp`), НЕ полный `resolveBattle()` — единая честная боевая
   модель общего мира, не два разных стиля боя под одной крышей.
   `banditArmy`/`BANDIT_TROOPS`/`banditTier` — дословно из index.html:
   3187-3195. Разбойники получают явный нулевой `B` (`atk:def:hp:matk:
   mdef:archer: 0`) — как `D.B={...:0}` в index.html:5139, не пустой объект
   (`sideStats` делает `(1+B.atk)` без `||0`-страховки, пустой объект дал бы
   NaN). Результат зачисляется игроку СРАЗУ при прибытии (не ждёт
   возвращения марша домой) — `hospitalSplit(attP,attLoss,"hospital")`
   (НЕ `"siege-attack"` — лагерь не чужой город) сразу пишет "лёгких" в
   `attP.troops` и "тяжёлых" в `attP.wounded`, а физически домой марширует
   только необожжённый остаток (`unitsSub(m.units,attLoss)` — сумма
   "лёгких"+"тяжёлых"+"мёртвых" и есть `attLoss`, так что это не двойной
   счёт, а то же число, разложенное на "уже дома" и "ещё в пути"). Победа —
   лагерь удаляется из `map_cells` целиком (без respawn, тот же честный
   пробел, что у истощённых точек), добыча — `banditLoot` (дословно
   `lootBase=1800*1.28^(lv-1)`, index.html:5148-5150), новое письмо
   `kind:"raid"`. Поражение — лагерь остаётся, письма без добычи.
4. **`mp-attack`/`mp-gather`** — лимит `marchSlots` теперь считает все три
   режима (`attack`/`gather`/`raid`) вместе — один общий пул "Отряды в
   поле", как и в одиночной игре.
5. **Панель «Общий мир»** — рубрика «Лагеря варваров» (список рядом, форма
   на T1-войска, как у «Атаковать»/«Собрать»), «Отряды в поле» показывает
   raid-марши отдельной подписью, новая рубрика «Лагеря» с письмами о
   разгроме/поражении и добычей.

**Честно НЕ перенесено:**

1. Опыт генерала (`BANDIT_XP`) и книги опыта (`bookDrop`) — в общем мире
   нет ни одного источника опыта генерала вообще (Фаза 7 — 5 очков висят
   неистраченными с самого создания игрока), начислять неоткуда.
2. ~~Респаун разгромленного лагеря~~ — закрыто в кусочке 3 (ниже).
3. Отзыв raid-марша на полпути (`mp-recall` проверяет `mode==="attack"`
   явно, gather/raid оба пока не поддержаны — тот же пробел, что и у сбора,
   тем же способом решаемый позже).

### Как применить

1. Задеплоить новую **`mp-raid`** — Dashboard → Edge Functions → Create
   Function → имя `mp-raid` → код из `functions/mp-raid/index.js` целиком.
2. Передеплоить **`mp-join`** — добавился `seedCampsAround`.
3. Передеплоить **`mp-tick`** — добавились `banditArmy`/`resolveBanditRaid`/

4. Передеплоить **`mp-attack`** и **`mp-gather`** — лимит `marchSlots`

5. Миграцию применять не нужно.

## Фаза 8, кусочек 1 — точки сбора ресурсов (mp-gather)

Первый кусочек «настоящей карты мира». Честные пробелы, ради которых
затевалась Фаза 8 (см. соответствующий раздел плана в самом начале
разработки): у общего мира до сих пор не было ни одной клетки `map_cells`
с реальным содержимым — атака целится по игроку, расстояние по прямой, ни
точек сбора, ни лагерей варваров, ни воды не существовало. Этот кусочек
закрывает первую из них — точки сбора ресурсов.

Приятная находка: таблица `map_cells` существует с самой первой миграции
(`0001_multiplayer_foundation.sql`) — заведена «на вырост», под именно узлы
сбора и лагеря/форты разбойников (`t: 'node' | 'camp' | 'fort'`), с RLS
`select using (true)` уже включённым. Просто до сих пор никто в неё не
писал. Новую миграцию заводить не пришлось.

**Что добавлено:**

1. **`mp-join`** — при создании НОВОГО игрока (не на каждый повторный join/
   опрос раз в 5с) сеет кольцо из 5 узлов вокруг его столицы
   (`seedNodesAround`): случайный угол, расстояние 8-25 клеток, уровень
   1-3 (честное упрощение — не hash-детерминированная плотность
   `nodeLevelAt`/`findFreeCellInChunk` из index.html:2968/3103, та заточена
   под чанки одного браузера), количество — та же формула, что и в
   `EV.nodeback` (index.html:3111): `6000 * 2.6^(lv-1)`. `upsert` с
   `ignoreDuplicates` — коллизия координат никого не роняет.
2. **Новая Edge Function `mp-gather`** — зеркало `sendMarch(...,"gather")`/
   узел-ветки `arriveMarch` (index.html:4646/5018-5039). Тот же
   марш-конвейер, что и у `mp-attack` (маршруты/`marchSlots`/travel по
   прямой), только вместо боя на месте — свой отсчёт сбора: считает
   грузоподъёмность отправленных войск, `take = min(load, amount)`,
   списывает `amount` с узла СРАЗУ при отправке (та же «бронь», что в
   index.html), скорость сбора — `GATHER_BASE_RATE` + честный `bonuses(p)`
   (`gather`/`gatherFW`/`gatherSG`/`march`/`load` — та же Фаза 6, только
   узкое подмножество полей, которые реально нужны сбору).
3. **`mp-tick`** — `applyMarchArrive` получил ветку `mode==="gather"`
   (`applyGatherStart` — переводит марш в `state:"gather"`, планирует
   `type:"gathered"` на момент завершения сбора, длительность которого уже
   посчитана в `mp-gather` при отправке). Новая `applyGathered` — марш
   разворачивается домой с добычей в `m.data.carry` (зеркало `EV.gathered`,
   index.html:4970-4977, без переноса respawn истощённой точки — см. ниже).
   `applyMarchHome` — зачисляет `m.data.carry` в `p.res` (зеркало
   `gain(p,m.carry)` из `EV.home`, index.html:4959-4964); у атакующих
   маршей этого поля нет и не будет, для них поведение не изменилось.
4. **`mp-attack`** — лимит `marchSlots` теперь считает `mode IN ("attack",
   "gather")` вместе (был только `"attack"`) — то же общее «Отряды в поле»,
   что и в клиенте одиночной игры (`renderFieldArmy` не отличает сбор от
   похода, кроме подписи).
5. **Панель «Общий мир»** — новая рубрика «Точки сбора» (список ближайших
   узлов, кнопка «Собрать» с формой на T1-войска, как у «Атаковать»);
   «Отряды в поле» теперь показывает и gather-марши отдельной подписью
   (идёт/собирает/везёт добычу); список маршей читается напрямую
   (`marches_select_all`, mode `attack` и `gather`), список узлов — тоже
   напрямую (`map_cells_select_all`, обе политики уже были в миграции 0001).

**Честные упрощения:**

1. Расстояние — по прямой, как и у `mp-attack`: местность (клетки помимо
   самих точек) не генерируется, обходить нечего.
2. Узел не занимается жёстко — `amount` списывается авансом, отдельного
   поля `busy`-блокировки не заводили (второй отряд на ту же точку просто
   получит меньше или наткнётся на «Точка истощена»).
3. ~~Респаун истощённой точки — НЕ перенесён~~ — закрыто в кусочке 3.
4. Отзыв похода на полпути (`mp-recall`) пока не работает для gather-марша
   — что делать с уже забронированной (списанной с узла) добычей при
   отзыве отдельный маленький разбор, не в этом кусочке; кнопка «Отозвать»
   в панели сейчас показывается только у боевых маршей.

## Фаза 2 — сервер сам считает время (готово, проверено на одном действии)

Пилотное действие — **набор войск** (единственное, чья цена/время не зависит
от бонусов рас/генералов/академии, кроме одного множителя скорости обучения,
который пока временно = 0, см. комментарий в `_shared/rules.js`). Три
Edge Function:

- **`mp-join`** — заводит (или возвращает уже существующего) игрока в общем
  мире по anon-uid. Тело: `{ race, nick? }`.
- **`mp-train`** — запускает набор войск (зеркало `startTrain` в
  index.html), списывает ресурсы, кладёт строку в `events`. Тело:
  `{ type: "inf"|"arc"|"cav"|"sie", tier: 1..5, n: number }`.
- **`mp-tick`** — вызывается `pg_cron` раз в минуту, разбирает наступившие
  события (`type:"train"`) НЕЗАВИСИМО от того, открыт ли у кого-то браузер —
  это и была цель Фазы 2. Остальные типы событий пока молча ждут своего case
  (не помечаются processed), будут добавляться по одному по мере переноса
  остальных действий.

Формулы (`troopCost`/`trainCap`/`trainDuration`/`canPay`/`pay`) вынесены в
`_shared/rules.js` буквально построчно с index.html и проверены тестом
против него (`node --check` + модульный тест на совпадение чисел) — это
самое начало общего модуля правил, упомянутого выше, пока только на объём
одного действия.

## Фаза 6 — bonuses(p): честное подмножество, реально действует

Центральный агрегатор бонусов клиента (`bonuses(p,defending)`, index.html:
3731-3789) — до сих пор всё, что от него зависело в общем мире
(`trainSpeed`, `heal`/`healSpeed`, `build`/`buildCostCut`, `prodAll`/
`prodFood`/`prodWood`/`prodStone`/`prodGold`), было временно = 0/1
("честная заглушка"). Эта фаза переносит и подключает настоящее
подмножество, которое общий мир способен посчитать ТОЧНО, без приближений:

1. **Расовый "минус"** (`RACES[race].minus`) — например, у людей золото
   добывается на 15% медленнее.
2. **Расовые эпохальные способности** (`RACE_EPOCHS`) — по числу открытых
   эпох ратуши (`epochOf`), плюс `defMods` 5-й эпохи только при обороне.
3. **Бонус "генерала по умолчанию"** — `genOf(p)=GENERALS[p.race][p.gen.id||0]`
   в клиенте всегда резолвится в ИНДЕКС 0 для игрока общего мира (`p.gen.id`
   всегда `null`, выбора генерала в MP ещё нет) — тот же дефолт, что у
   игрока одиночной игры, который ещё не открывал вкладку "Генерал".
   `GENERALS_DEFAULT` — эти 4 записи (по расе), не вся таблица `GENERALS`.
4. **Дерево исследований** (`ACADEMY_TREE[*].field/effects`, по `p.tech`) —
   уже перенесённая в Фазе 5 механика теперь наконец подключена к самим
   бонусам: исследованные узлы реально прибавляют к добыче/обучению/etc.

**Что НЕ подключено — и почему это математически, а не приблизительно ноль**:
талантовые бонусы генерала (w1-w5/d1-d5/g1-g3/g4-g5) и `GENERAL_TREE`
(город/армия) читают ТОЛЬКО `p.gen.tal`, которое в общем мире всегда `{}`
(системы вложения очков таланта нет вообще) — вклад этих блоков строго 0,
не приближение, поэтому они просто опущены, а не скопированы бесполезно.

**Что подключено практически** (в самих Edge Function): `production()`
(добыча по времени — `mp-join`/`mp-train`/`mp-heal`/`mp-build`/`mp-research`,
через `syncRes`), `trainDuration` (`mp-train`), `healUnitCost`/`healDuration`
(`mp-heal`), `buildCost`/`buildDuration` (`mp-build`). **Что осознанно
оставлено на потом**: `march` (скорость марша — `mp-attack`/`mp-scout`/
`mp-recall`), боевые бонусы (`atk`/`def`/`atkInf`/.../`wallBonus`/`counter`/
`firstStrike`/`raise`/`mercy`/`hosp` — упрощённый `resolvePvp` в `mp-tick`),
`researchSpeed` (`mp-research`), `scoutBonus` (глубина донесения разведки) —
каждое из них требует более широкой правки уже переносимой механики, не
просто подстановки числа, отдельные следующие шаги.

**ИСПРАВЛЕННЫЙ ПОПУТНО БАГ**: `bonuses()`/`nodeVisibleFor()` читают `p.race`
с ОДНОГО объединённого объекта игрока — но раса всегда жила только в
колонке `players.race`, а не в самом `state` (JSONB), который эти функции
получают как единственный аргумент. До этой правки `p.race` внутри ЛЮБОЙ
такой функции был `undefined` — расовые бонусы просто не работали ни для
кого, и (что серьёзнее) ВСЕ race-гейтед узлы Академии (все 8 венцов)
казались недостижимыми — при этом `mil_crown_*` (`gen:0`) на самом деле
достижимы без выбора генерала (см. следующий абзац), просто из-за этого
бага их искусственно прятало ещё и `n.race!==p.race`. Исправлено: `mp-join`
теперь дублирует `race` в `state` для новых игроков, и каждая функция,
читающая `p.race`, самоисцеляется (`p.race = p.race || row.race`) для
старых записей.

**Попутно исправлено неверное заявление в комментариях Фазы 5**: раньше
здесь и в `mp-research`/`_shared/rules.js` было сказано, что ВСЕ 8 венцов
(`eco_crown_*`/`mil_crown_*`) недостижимы без генералов. На деле верно
только для `eco_crown_*` (`gen:1`, не совпадает с дефолтным `p.gen.id||0=0`).
У `mil_crown_*` (`gen:0`) — совпадает, эти 4 узла честно достижимы любой
подходящей расе после прохождения row-гейтинга, генерал тут вообще ни при
чём — и теперь, когда `effects` подключены (см. выше), они реально работают.

Клиентская панель «Общий мир» (превью "Добыча/час") тоже обновлена — вместо
своей отдельной формулы-приближения теперь напрямую зовёт НАСТОЯЩИЙ
`production(p)` одиночной игры (тот самый файл, не копия) через тот же
приём `pShim`, что и у рубрики «Академия» — числа гарантированно совпадают
с тем, что реально спишет/начислит сервер.

### Как применить

Код изменился в пяти функциях (везде добавился блок `bonuses()`+`ACADEMY_TREE`

## Фаза 7 — выбор полководца (mp-pickgen)

Первый настоящий кусочек системы генералов. Раньше `bonuses()` во всех 9
копиях (`_shared/rules.js` + `mp-train`/`mp-heal`/`mp-build`/`mp-join`/
`mp-research`/`mp-attack`/`mp-recall`/`mp-scout`/`mp-tick`) применял только
`GENERALS_DEFAULT[p.race]` — ровно ОДНУ (нулевую) запись на расу, потому что
`p.gen.id` физически не мог стать чем-то другим: выбирать было негде. Теперь
`p.gen.id` можно реально выбрать — новая функция **`mp-pickgen`**, зеркало
экрана "Выбор полководца" (`foGen()`, index.html:7414-7426) и его клика
(index.html:7951-7953): одноразово, бесплатно, необратимо, `id: 0|1`.

`GENERALS_DEFAULT` (4 записи) переименован обратно в полный `GENERALS`
(index.html:2283-2344, 8 записей — оба генерала на расу), и строка внутри
`bonuses()` теперь честно читает `GENERALS[p.race][(p.gen&&p.gen.id)||0]`
вместо захардкоженного индекса 0 — с защитой от легаси-состояний без `.gen`
вовсе (та же идиома `X && X.field`, что и у `p.b`/`p.b.hall` в Фазе 6). Пока
никто не выбрал генерала (`p.gen.id==null`, как задаёт `mp-join`), поведение
не меняется ни на бит — по-прежнему индекс 0, ровно как раньше.

Клиентская панель «Общий мир» получила новую рубрику «Полководец» —
честно переиспользует ту же самую глобальную таблицу `GENERALS` и функции

**Что НЕ перенесено, и почему это честный пробел**: ~~уровень/опыт

## Фаза 6, продолжение — глубина донесений разведки (scoutBonus)

Последний из "маленьких" бонусов — оказался НЕ тем, чем казался. Заголовок
`mp-scout` изначально заявлял, что глубина донесения зависит от
`bonuses(p).scoutBonus`, ждущей переноса bonuses(). На деле проверка кода
клиента (`scoutSnapshot`, index.html:5237-5282) показала: глубина донесения
(`se`) — это СЫРОЙ уровень `p.tech.mil_scout2` (0-5), напрямую, без единого
bonuses()-вызова. Поле `scoutBonus` внутри `bonuses()` — отдельная,
декоративная величина (сумма `mil_scout1`+`mil_scout2`, до +50%), которая
нигде в клиенте не читается для глубины разведки. Раз реальный переключатель
— это уже перенесённый `p.tech.mil_scout2`, глубину можно было подключить
сразу же, без ожидания какого-либо ещё переноса.

Подключено в `applyScoutArrive` (mp-tick) — те же пороги `se>=1..5`, что и в
`scoutSnapshot`/`scoutReportHtml` одиночной игры:

- `se>=1`: запасы (`res`), общее число войск (округлённое до сотни на
  ступенях 1-2, точное с se>=3).
- `se>=2`: уровень стены, уровень полководца (`genLv` — честно `null`,
  генералы не перенесены).
- `se>=3`: уровень Академии, раскладка войск по РОДАМ (`byType`).
- `se>=4`: уровень гарнизонной башни, раскладка по ТИРАМ (`byTier`).
- `se>=5`: раненые в лазарете (реальное число), таланты/снаряжение
  полководца (`genTal`/`gearPower`/`gear` — честно `null`/`0`/`[]`).

**Честно НЕ перенесено**: `wallHp`/`wallMax` (se>=2) — прочность стены как
отдельный, регенерирующий со временем пул HP (`p.wallHp` в одиночной игре,
`syncWall`) — это отдельная механика, которой в общем мире вообще нет: там
есть только УРОВЕНЬ стены (`p.b.wall`), сама прочность не отслеживается.

Клиентская панель «Общий мир» (рубрика «Разведка») тоже обновлена — вместо
плоского "Ратуша N ур. · войск: N" показывает донесение по тем же ступеням,
что и одиночная игра (без блочной вёрстки — короче, для почты).

## Фаза 6, продолжение — боевые бонусы в упрощённом PvP

Самая крупная из оставшихся частей `bonuses()` — боевые бонусы
(`atk`/`def`/`matk`/`mdef`/`hp` по каждому роду войск, `archer`, `wallBonus`,
`hosp`/`mercy`) теперь подключены в `resolvePvp`/`sideStats`/`dmgTo`/

**Что реально подключено** (дословно как в `sideStats`/`dmgTo`
index.html:3974-4014/4194-4213):

1. Per-type атака/защита/магатака/магзащита (`atkInf`/`defArc`/`matkCav`/...,
   от исследований, например `mil_atk_inf1`).
2. Общие `atk`/`def`/`matk`/`mdef`/`hp` (раса/эпоха/дефолтный генерал/
   дерево исследований — например, дефолтный генерал человека всегда даёт
   `atk+.15/def+.08`).
3. `archer` (бонус атаки лучников, например расовая способность эльфов).
4. `wallBonus` защитника (index.html:4142 `1+wallDefBonus(lv)*(1+bonus)`) —
   раньше был захардкожен нулём.
5. `hosp`/`mercy` в `hospitalSplit` (расширяют ёмкость лазарета) — `hosp`
   математически всегда 0 в общем мире (доступен только через talent-очки
   генерала, которых в MP не существует), `mercy` реален (например, эпоха 3
   нежити).

**Что НЕ подключено, и почему это отдельная задача, не эта правка**: раунды,
погода, слом дисциплины, полководцы (урон от/по ним), поднятие нежити прямо
в бою (`raise`/`raiseHurt`), контрудар гарнизона (`counter`, дворфские
defMods), первый залп без ответа (`firstStrike`, эльфийские defMods) — все
это существует только внутри `resolveBattle()`'s раундового цикла, которого
здесь как не было, так и нет (см. заголовок PvP-блока). `researchSpeed`
(влияет на длительность исследований, mp-research) и `scoutBonus` (глубина
донесения разведки, mp-scout) тоже пока не подключены — оба требуют
доработки уже перенесённой, но пока честно упрощённой механики.

`resolvePvp`/`hospitalSplit` теперь принимают ПОЛНЫЕ объекты игрока
(`race`+`b`+`gen`+`tech`), не голые строки расы — им нужны настоящие
`bonuses(attP)`/`bonuses(defP,true)` (защитник считается с `defending=true`
— 5-я эпоха, defMods). Попутно `bonuses()` во ВСЕХ 9 копиях (rules.js +
mp-train/mp-heal/mp-build/mp-join/mp-attack/mp-recall/mp-scout/mp-tick)
защищена от отсутствующего `p.b` (`epochOf(p.b && p.b.hall)` вместо
`epochOf(p.b.hall)`) — раньше упала бы с `Cannot read properties of
undefined` на легаси-состоянии без `state.b` вовсе.

### Как применить

Две функции целиком — **`_shared/rules.js`** (если деплоите через CLI) и
**`mp-tick`** (Dashboard) — заменить содержимым из репозитория. Остальные
7 функций (`mp-train`/`mp-heal`/`mp-build`/`mp-join`/`mp-attack`/`mp-recall`/
`mp-scout`) получили только защитную правку `p.b && p.b.hall` внутри уже
имеющегося `bonuses()` — тоже стоит передеплоить при случае, но это не
критично прямо сейчас (баг проявлялся только на состояниях без `state.b`
вовсе, что редкость). SQL не трогать.

## Фаза 6, продолжение — march (скорость марша)

Прямое продолжение предыдущего раздела: `bonuses(p).march` (раса/эпоха
рас/дефолтный генерал/дерево исследований `mil_march1`/`mil_march2`)
теперь тоже реально считается, а не заглушка `=1`. Подключено во всех
трёх местах, где марш вообще существует:

- **`mp-attack`** — `marchSpeed(units, race, marchBonus)` получает
  `B.march` при отправке похода.
- **`mp-recall`** — тот же `marchSpeed` с `B.march`, посчитанным от
  состояния отправителя, при развороте похода на полпути.
- **`mp-scout`** — `baseSpeed = MARCH_SPEED_SCALE * B.march` (лазутчик
  налегке без расовых модификаторов конкретных родов войск, но общий
  `march`-бонус применяется так же, как к обычному маршу).

Попутно та же правка `p.race = p.race || row.race`, что и у остальных
функций Фазы 6 (`mp-attack`/`mp-scout` читали `attP.race` из `state`,
где расы могло не быть у легаси-записей; `mp-recall` уже безопасно читал
`attRow.race` с самой строки, но для `bonuses()` тоже нужен `attP.race`).

### Как применить

Три функции — **`mp-attack`**, **`mp-recall`**, **`mp-scout`** —
Dashboard → Edge Functions → заменить содержимое актуальным кодом из
репозитория. `mp-tick`/SQL не трогать.

## Фаза 5, шестой кусочек — дерево исследований Академии (mp-research)

Самый крупный кусок правил, перенесённый на сервер за один шаг: **ACADEMY_TREE**
целиком — ~79 узлов на два раздела (eco/mil), с настоящими таблицами
стоимости/времени/мощи (38 таблиц `RS_*`, дословные RoK-числа) и настоящей
разблокировкой по дереву. Пятая Edge Function — **`mp-research`** (зеркало
`startResearch(p,id)` из index.html:5848-5863), плюс новый `case` в `mp-tick`
(`type:"research"`, зеркало `EV.research`, index.html:4840-4844) и рубрика
«Академия» в панели «Общий мир».

**Особенность, которую легко упустить (и которая перенесена как есть, а не
упрощена)**: разблокировка узла (`researchLocked`/`rowGate`) НЕ проверяет
впрямую `n.requires` — она смотрит, закончен ли ЦЕЛИКОМ предыдущий визуальный
РЯД дерева (`computeRows` группирует узлы одной "глубины" — `nodeDepth`,
посчитанной по цепочке `requires`, — в ряды по `ROW_SIZES=[4,3,4,2]` штук для
красоты интерфейса). `n.requires` используется ТОЛЬКО для расчёта глубины
узла, а не как прямой список условий — так ведёт себя сам index.html, здесь
просто зеркалируется.

**Требует построенную Академию (`p.b.academy>0`)** — сам `startResearch(p,id)`
в index.html этого явно не проверяет (полагается на то, что кнопка вообще не
появится без неё), но у сервера нет такой страховки со стороны UI, поэтому в
`mp-research` эта проверка добавлена явно.

**Честно НЕ входит в этот шаг:**

1. `bonuses(p).researchSpeed` (влияет на длительность через
   `researchTime(n,lv)/(1+B.researchSpeed)`, index.html:5859) — временно = 0,
   та же заглушка, что и everywhere else в общем мире; `researchTime(n,lv)`
   показывается и применяется как есть, без деления.
2. Сами ЭФФЕКТЫ исследований (`n.field`/`n.effects` — надбавки к добыче/бою/
   etc через `bonuses()`) — `bonuses()` как таковая ещё не перенесена на
   сервер вообще. Переносится только МЕХАНИКА исследования (набрать очки,
   продвинуться по дереву — `p.tech` заполняется настоящими уровнями);
   подключение самих бонусов в `production()`/`dmgTo()`/`marchSpeed()` и т.д.
   — отдельный следующий шаг.
3. gen-гейтед "венцы" (`eco_crown_*`/`mil_crown_*` с полем `gen:0|1`) —
   **исправление**: изначально здесь было заявлено, что ВСЕ 8 венцов
   недостижимы без генералов — это оказалось верно только для половины.
   Генералы на сервер не перенесены (`p.gen.id` всегда `null`), поэтому
   `p.gen.id||0` всегда 0. У `eco_crown_*` `gen:1` (0≠1 → действительно
   невидим). У `mil_crown_*` `gen:0` (0=0 → **видим**) — эти 4 узла честно
   достижимы любому игроку подходящей расы после row-гейтинга; см. Фазу 6
   ниже, где их `effects` тоже подключены и реально действуют.

### Как применить

1. Задеплоить новую **`mp-research`** — Dashboard → Edge Functions → Create
   Function → имя `mp-research` → код из `functions/mp-research/index.js`
   целиком (самодостаточен, как и остальные функции).
2. Передеплоить **`mp-tick`** — добавился разбор `type:"research"`.
3. Ничего в SQL менять не нужно.

## Фаза 4, девятый кусочек — отзыв похода на полпути (mp-recall)

До сих пор поход, однажды отправленный (`mp-attack`), нельзя было ни
отменить, ни развернуть раньше срока — оставалось либо ждать боя, либо
просто закрыть вкладку. Новая Edge Function **`mp-recall`** — зеркало
`recallMarch(m)` (index.html:4770-4780): отряд разворачивается ОТ
ТЕКУЩЕЙ ТОЧКИ на маршруте (линейная интерполяция между домом и целью по
доле пройденного времени — `marchPos(m)` в клиенте делает то же самое
покадрово вдоль настоящего пути), не мгновенно из дома и не от цели —
чем дальше отряд уже прошёл, тем дольше идти обратно, той же формулой
скорости, что и исходный марш.

Работает только для похода в пути (`mode:"attack"`, `state:"go"`) —
уже возвращающийся отзывать нечего (в клиенте `recallMarch` тут просто
молча выходит, но это фоновый вызов без ответа пользователю; здесь это
прямое действие по кнопке, поэтому честнее вернуть ошибку). Изначальное
событие `march_arrive` (на исходное время прибытия) отдельно не
отменяется — просто становится безвредным no-op'ом за счёт уже
существующей защиты `mp-tick` ("уже разобрано/отменено", проверка
`m.state!=="go"`), той же, что защищает от двойной обработки где угодно
ещё; никакой новой логики отмены заводить не пришлось.

Панель «Общий мир»: кнопка «Отозвать» у каждого похода в разделе «Отряды
в поле», видна только пока он ещё идёт (не у уже возвращающихся).

### Как применить

1. Создать новую Edge Function **`mp-recall`** (тело — `supabase/
   functions/mp-recall/index.js`, самодостаточный, копия как у остальных).
2. `mp-tick`/`mp-train`/`mp-build`/`mp-attack`/`mp-heal`/`mp-scout`/
   `mp-join`/SQL не трогать — вся логика самоограничена в новой функции,
   опирается на уже существующую защиту тикера от повторной обработки.

## Фаза 4, восьмой кусочек — разведка чужого города (mp-scout)

Здание «Разведка» (`p.b.scout`) уже строилось и считалось в мощь (Фаза 5,
четвёртый кусочек), но сама механика не существовала — нападать
приходилось вслепую, не зная даже, есть ли у цели хоть один боец. Новая
Edge Function **`mp-scout`** — зеркало `sendScout(p,tx,ty)`/`EV.scouted`
(index.html:4704-4730/4877-4893): лазутчик не занимает слот похода (свой
отдельный лимит одновременных вылазок — `SCOUT_TABLE.scouts`, 1 на
уровнях 1-4, 2 на 5-10, 3 на 11+), бежит заметно быстрее армии
(`SCOUT_SPEED_MULT=2.2`, плюс надбавка от прокачки самого здания —
`SCOUT_TABLE.bonus`), без войск с собой, без боя, и не возвращается домой
— снимает показания на месте и тут же гасит марш (то же самое, что и в
клиенте: "он один и налегке, возвращать домой нечего").

Честные упрощения:
1. Цель — игрок по id, не клетка карты (та же причина, что и у
   `mp-attack` — `map_cells` не сгенерированы в общем мире).
2. Глубина донесения (`scoutSnapshot`, index.html:5237-5282) зависит от
   технологии «Маскировка» (`p.tech.mil_scout2`) — целого дерева
   исследований, которое на сервер ещё не перенесено вообще (самая
   большая оставшаяся задача этого переноса). Честная заглушка — `se=0`
   всегда, то есть донесение несёт РОВНО то, что даёт `se=0` в реальной
   формуле: только общее число войск цели, без разбивки по родам/тирам,
   без запасов, без стены, без полководца — не урезанная имитация, а та
   же формула на минимальном тире.
3. `power(q)` (общая мощь цели) не перенесена — вместо неё в донесении
   просто уровень ратуши, самостоятельный честный показатель силы,
   который уже есть на сервере.

`mp-tick` умеет новый `type:"scout_arrive"` (`applyScoutArrive`) — пишет
письмо (`kind:"scout"`) с составом донесения и сразу удаляет марш
(никакого `march_home`, лазутчик не возвращается). Цель под щитом мира
всё равно разведывается (щит блокирует только атаки, не разведку, как и
в клиенте) — донесение честно помечает `shielded:true`.

Панель «Общий мир»: кнопка «Разведать» у каждого соседа (видна только
если разведка уже построена), новая рубрика «Разведка» с донесениями.

### Как применить

1. Создать новую Edge Function **`mp-scout`** (тело — `supabase/functions/
   mp-scout/index.js`, самодостаточный, копия как у остальных).
2. Задеплоить обновлённый **`mp-tick`** — добавился `case "scout_arrive"`.
3. `mp-train`/`mp-build`/`mp-attack`/`mp-heal`/`mp-join`/SQL не трогать.

## Фаза 4, седьмой кусочек — лечение раненых (mp-heal)

Прямое продолжение прошлого шага: тяжелораненые (`p.wounded`) начали
копиться в бою, но забрать их обратно было неоткуда — новая **`mp-heal`**
закрывает это. Зеркало `startHeal(p,type,tier,n)`/`EV.heal`
(index.html:5795-5809/4867-4873) — та же одна очередь лечения на игрока
(`p.heal`, отдельная от очереди набора `p.train[type]`), тот же
`canPay`/`pay`/`healDuration`. Лечение стоит вдвое дешевле и идёт вдвое
быстрее полного набора того же юнита и никогда не требует золота
(`healUnitCost`/`healUnitTime`, index.html:2840/2844); предел за раз —
`trainCap` от максимального (не суммарного) уровня среди построенных
участков госпиталя, ровно как в клиенте. Только тир 1 — в общем мире
набор войск тоже только тира 1, другим тирам взяться неоткуда.

По пути перенесён и сам `healUnitCost`/`healUnitTime`/`healDuration` в
`_shared/rules.js` — включая честный разбор направления формулы
`healSpeedBonus` (числитель, не `(1+bonus)` в знаменателе, как у
`trainSpeed`/`build` — в index.html эту формулу когда-то дважды чинили в
неверную сторону подряд, тот же разбор перенесён в комментарий).

`mp-tick` умеет новый `type:"heal"` (`applyHeal`) — на завершении раненые
переезжают из `p.wounded` в `p.troops`, `p.heal` очищается; количество
клампится по факту на момент завершения, тот же принцип "текущее
состояние, не снимок", что и у `march_arrive`.

Панель «Общий мир» — новая рубрика «Лазарет» (видна только если есть кого
лечить или лечение уже идёт), с тем же ползунком/кнопкой, что и «Набор
войск». Как и в «Добыча/час», здесь НЕ вызывается настоящий `healUnitCost/
healDuration` из одиночной игры — те читают `bonuses(p)`, а у панели нет
полноценного объекта игрока — вместо них та же лёгкая переформулировка без
бонусов, что и на сервере (`healBonus=1`/`healSpeedBonus=1`).

### Как применить

1. Создать новую Edge Function **`mp-heal`** (тело — `supabase/functions/

## Фаза 4, четвёртый кусочек — стена защитника в бою

Бой (`resolvePvp`/`dmgTo`) раньше вообще не учитывал стену защитника, хотя
уровень стены уже строится (Фаза 5) и участвует в подсчёте мощи — штурмовать
что стену 0, что стену 25 уровня было одинаково больно. Теперь честно
перенесены `tableAt`/`wallDefBonus` (index.html:2895-2911, дословно, вплоть
до дробной интерполяции по уровню) и подключены в `dmgTo` ровно так, как в
`resolveBattle()` (index.html:4142/4208-4209): множитель `defWall = 1 +
wallDefBonus(lv)*(1+bonus)` умножает ИМЕННО дробь `def/70` внутри
смягчения урона (`mitig = 1 + (def/n)/70 * defWall`), а не всё выражение
целиком — важная деталь, легко перепутать. `bonus` (`D.B.wallBonus`, из
`bonuses()`) по заведённой в этом файле традиции временно = 0, как и все
остальные `bonuses()`-члены везде в общем мире.

Стена защищает **только защитника** — как и в клиенте (`dA=dmgTo(A,sa,sd,
wallMul,...)`, но `dD=dmgTo(D,sd,sa,1,...)`): своя стена атакующего его
марширующий отряд не прикрывает. Уровень стены читается из `p.b.wall`
защитника прямо на момент боя (тот же принцип «текущее состояние, не
снимок», что и у самого гарнизона со второго кусочка); отсутствие `p.b`
у совсем старой записи не роняет бой — просто трактуется как стена
уровня 0 (без бонуса).

Форма атаки в панели «Общий мир» больше не пишет «без стены» — стена
теперь настоящая; остаются честно незаконченными только полководцы и
погода (полный `resolveBattle()` — отдельная большая задача).

### Как применить

## Фаза 4, второй кусочек — настоящий марш со временем в пути

Раньше `mp-attack` бил мгновенно (см. первый кусочек ниже) — теперь
заводит настоящий марш: зеркало `sendMarch`/`arriveMarch`/`recallMarch`/

march` временно = 1 (та же заглушка, что и everywhere else).

новой SQL/pg_cron-настройки не понадобилось):

1. **`mp-attack`** — списывает отправленную часть гарнизона из дома сразу

   `W.players` по факту прибытия). Если цель пропала или встала под щит —
   бой не случается, отряд просто разворачивается (зеркало `recallMarch`

   не идёт домой — марш удаляется сразу же.
3. **`mp-tick`**, `type:"march_home"`: выжившие вливаются обратно в
   домашний гарнизон, строка `marches` удаляется.

Панель «Общий мир»: форма атаки честно называет расстояние и то, что
марш/время в пути уже настоящие; новый раздел «Отряды в поле» — список
собственных походов с обратным отсчётом (свои же строки `marches`,
`marches_select_all` из миграции 0001 уже разрешает читать их напрямую).

## Фаза 5, четвёртый кусочек — добыча ресурсов по времени

Ресурсы в общем мире теперь **растут сами**, как и обещано в третьем
кусочке — закрывает главный оставшийся пробел. Перенесена "ленивая
экономика" index.html (`syncRes`/`production`/`plotFillCap`, index.html:
3790-3860): ничего не тикает само по себе на сервере (никакого нового
`pg_cron`-задания не понадобилось) — добыча досчитывается по разнице
`now - resAt` при КАЖДОМ обращении к игроку: `mp-join` (в том числе на
каждый опрос — вкладка «Общий мир» дёргает `mp-join` раз в 5с, теперь это
ещё и способ получить свежие ресурсы) и перед `canPay`/`pay` в `mp-train`/
`mp-build`, ровно как в одиночной игре, где та же функция вызывается при
любом чтении/трате, а не тикает по таймеру.

Как и раньше, участки 1-3 у ферм/лесопилок/каменоломен/шахт ещё не
перенесены — добыча считается только с участка 1 (столько же, сколько уже
можно построить, см. третий кусочек). `bonuses(p).prodAll/prodFood/...`
(зависят от рас/генералов/академии) — та же временная заглушка (=0), что и
везде: числа приблизительные, но структурно верные, реальные бонусы
подключатся вместе с полным переносом `bonuses()`.

Важный нюанс, унаследованный из одиночной игры (не баг): добыча за один
"синк" ограничена `plotFillCap` участка — как в RoK, где добыча копится до
"ёмкости" и дальше не растёт, пока не забрать. Если не заходить очень
долго, при возврате начислится не безгранично накопленное, а максимум
вместимости участка (тот же принцип, что в одиночной игре).

Новых Edge Functions нет — изменились существующие: `mp-join` (досчитывает
и сохраняет ресурсы при каждом ответе; у новых игроков `resAt` теперь
верно равен моменту создания, а не 0 — иначе первый же синк решил бы, что
прошли миллиарды секунд с эпохи Unix), `mp-train`/`mp-build` (синк перед
проверкой оплаты). Панель в игре показывает "Добыча/час" рядом с текущими
ресурсами (клиентский превью через уже существующий глобальный `prodRate`,
без вызова полного `bonuses()`, чтобы не тянуть весь игровой объект игрока
ради одной цифры).

### Как применить

Изменились `mp-join`, `mp-train`, `mp-build` — передеплоить все три тем же
способом (Dashboard → Edge Functions → имя функции → заменить код на

lumber) неверной формой — почищено, самоисцеление в `mp-build` теперь
обобщено на ЛЮБОЕ multi-здание, а не захардкожено под hospital.

**Важная честная оговорка**: сама добыча ресурсов от уровня этих зданий
(`production()` в index.html, тикает по реальному прошедшему времени через
`resAt`) **ещё не перенесена** — это другой тип механики (непрерывное
накопление, а не разовое событие вроде постройки/набора) и заслуживает
отдельного шага со своими тестами (граница вместимости склада, безопасность
при параллельных тратах). Пока ферму/лесопилку/каменоломню/шахту можно
строить, но ресурсы в общем мире по-прежнему не растут сами — про это прямо
написано в самой вкладке «Общий мир».

### Как применить

Код `mp-build` и `mp-join` изменился (`mp-tick` — только добавился
комментарий, но проще передеплоить и его тем же актуальным содержимым) —
те же три функции, что и раньше, просто с новым содержимым:

1. **`mp-build`** — Dashboard → Edge Functions → `mp-build` → заменить код
   на актуальный из `functions/mp-build/index.js` → Deploy.
2. **`mp-join`** — то же самое, актуальный код из `functions/mp-join/index.js`
   (чинит форму госпиталя для новых игроков).
3. **`mp-tick`** — то же самое, актуальный код из `functions/mp-tick/index.js`.

SQL/секрет трогать не нужно.

## Фаза 5, первый кусочек — постройки казарм/стрельбища/конюшни/мастерской

Раньше единственные 4 здания, разблокирующие набор войск (barracks/range/
stable/siege), можно было поднять только вручную через SQL — теперь это
делает сама вкладка «Общий мир» в игре. Четвёртая Edge Function:

- **`mp-build`** — зеркало `startBuild` из index.html (ограничено этими 4
  зданиями — ни одно не multi-участок, `HALL_REQ` их не гейтит). Тело:
  `{ bk: "barracks"|"range"|"stable"|"siege" }`. Проверяет: не занята ли
  бригада, не идёт ли уже набор в этом же здании, потолок 25 уровень,
  требуемый уровень ратуши, хватает ли ресурсов — списывает и кладёт
  событие `type:"build"` в `events`.
- **`mp-tick`** обновлён — теперь разбирает и `type:"build"` (зеркало
  `EV.build`), не только `type:"train"`.

`bonuses(p).build`/`buildCostCut` (зависят от рас/генералов/академии) —
та же временная заглушка (1/0), что и `trainSpeed` в Фазе 2, тем же
способом помечена в `_shared/rules.js`. Таблицы `BARRACKS_TABLE`/
`SIEGE_TABLE` — буквальная копия из index.html, сверены тестом на точное
совпадение чисел.

Остальные 11 построек (ратуша, стена, ферма, лесопилка, каменоломня,
шахта, академия, склад, лазарет, дозор, разведка) — следующие шаги,
каждое отдельным переносом.

### Как применить

Те же шаги, что в Фазе 2, плюс:

1. Задеплоить **`mp-build`** — Dashboard → Edge Functions → Create Function
   → имя `mp-build` → код из `functions/mp-build/index.js` целиком
   (самодостаточен, как и остальные три).
2. Передеплоить **`mp-tick`** — код обновился (добавился разбор
   `type:"build"`), нужно заменить содержимое существующей функции на
   актуальное из `functions/mp-tick/index.js`.
3. Ничего в SQL менять не нужно — `0002_phase2_tick.sql` уже накатан,
   pg_cron продолжает дёргать тот же `mp-tick` по тому же расписанию.

Дальше (Фаза 3) — то же самое, но видно всем игрокам сразу, и построек/
действий станет больше.
