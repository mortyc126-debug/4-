# Общий мир — план переделки

Цель: настоящий общий мир на несколько живых игроков (как в RoK), где события
(постройка, сбор, бой, приход похода) разрешаются сервером сами по себе, даже
если ни один игрок сейчас не в игре. Делается поэтапно — на каждом шаге игра
остаётся рабочей, однопользовательский режим не ломается.

## Почему так

Сайт — статика на Render (`render.yaml`), собственного постоянно работающего
процесса завести негде. Значит бэкенд — это Supabase: Postgres как источник
правды + Edge Functions на каждое действие + `pg_cron`, который тикает сам по
расписанию и досчитывает события, независимо от того, открыт ли у кого-то
браузер.

## Фазы

1. **Фундамент (эта миграция, `0001_multiplayer_foundation.sql`)** — таблицы
   `worlds`/`players`/`map_cells`/`marches`/`events`/`mail` + RLS. Ничего в
   `index.html` ещё не меняется, существующий однопользовательский сейв
   (`saves`, по `device_id`) работает как раньше и не трогается.
2. **Сервер считает время** — `pg_cron` + Edge Function-тикер, который
   разбирает `events` по расписанию (аналог `EV{...}` в index.html, только на
   сервере). Проверяется на 1-2 действиях, не на всех сразу.
3. **Общая видимость** — все игроки читают одни и те же `players`/`map_cells`
   вместо приватных ботов у каждого в браузере; новый игрок попадает в тот же
   мир, не в свой собственный.
4. **PvP по-настоящему** — бой между живыми игроками считает сервер один раз,
   результат одинаков у обеих сторон.
5. **Полный перенос действий** — постройки/войска/академия/крафт и т.д. по
   одному переезжают на сервер (Edge Function на каждое), клиент становится
   тонким: жмёт кнопку → ждёт ответ сервера → рисует.

Расчётные формулы (стоимость построек, боя, сбора и т.д.) уже написаны как
чистые JS-функции в `index.html` — их предполагается не переписывать заново
на SQL, а вынести в общий модуль, который сможет использовать и браузер (для
мгновенного предпросмотра), и Edge Function (Deno, тот же JS/TS) — как
единственный источник правды по правилам игры.

## Как применить эту миграцию

У сессии, что готовила эти файлы, нет доступа к самому проекту Supabase —
только публичный `anon`-ключ, что уже в `index.html` (им нельзя менять
схему). Применить может только тот, у кого есть доступ к дашборду:

1. Открыть проект в [supabase.com/dashboard](https://supabase.com/dashboard)
   → **SQL Editor**.
2. Вставить содержимое `migrations/0001_multiplayer_foundation.sql` целиком →
   **Run**.
3. Включить **Anonymous sign-ins**: Authentication → Providers → Anonymous →
   Enable (нужно для Фазы 1 — настоящий `auth.uid()` вместо голого
   `device_id`, тот же нулевой порог входа, что и сейчас).

Готово — таблицы появятся, но игра пока не меняется: следующий шаг (Фаза 2)
описан ниже.

## Фаза 2 — сервер сам считает время (готово, проверено на одном действии)

Пилотное действие — **набор войск** (единственное, чья цена/время не зависит
от бонусов рас/генералов/академии, кроме одного множителя скорости обучения,
который пока временно = 0, см. комментарий в `_shared/rules.js`). Три
Edge Function:

- **`mp-join`** — заводит (или возвращает уже существующего) игрока в общем
  мире по anon-uid. Тело: `{ race, nick? }`.
- **`mp-train`** — запускает набор войск (зеркало `startTrain` в
  index.html), списывает ресурсы, кладёт строку в `events`. Тело:
  `{ type: "inf"|"arc"|"cav"|"sie", tier: 1..5, n: number }`.
- **`mp-tick`** — вызывается `pg_cron` раз в минуту, разбирает наступившие
  события (`type:"train"`) НЕЗАВИСИМО от того, открыт ли у кого-то браузер —
  это и была цель Фазы 2. Остальные типы событий пока молча ждут своего case
  (не помечаются processed), будут добавляться по одному по мере переноса
  остальных действий.

Формулы (`troopCost`/`trainCap`/`trainDuration`/`canPay`/`pay`) вынесены в
`_shared/rules.js` буквально построчно с index.html и проверены тестом
против него (`node --check` + модульный тест на совпадение чисел) — это
самое начало общего модуля правил, упомянутого выше, пока только на объём
одного действия.

### Как применить

Эта сессия не может задеплоить функции сама — у неё в принципе нет сетевого
доступа к `api.supabase.com` (заблокировано политикой окружения, не вопрос
токена/прав), поэтому единственный путь — руками, через Dashboard, или
через Supabase CLI с вашего компьютера.

1. Задеплоить три функции — **Dashboard → Edge Functions → Create Function**,
   имя функции = имя папки (`mp-join`, `mp-train`, `mp-tick`, ровно так, без
   суффиксов — это часть URL, который уже прописан в миграции 0002). Код —
   содержимое `functions/mp-join/index.js`, `mp-train/index.js`,
   `mp-tick/index.js` целиком. Эти файлы самодостаточны (без относительных
   импортов на `_shared/` — Dashboard-редактор их не подтягивает, формулы
   вклеены прямо внутрь с пометкой источника). Есть свой Supabase CLI —
   можно и им (`supabase functions deploy mp-join` и т.д.), тогда относительный
   импорт из `_shared/` тоже сработает, отдельно ничего готовить не надо.
2. Project Settings → Edge Functions → Secrets → добавить
   `MP_TICK_SECRET` = случайная строка (например, `openssl rand -hex 20`).
3. Вставить `migrations/0002_phase2_tick.sql` в SQL Editor, заменить
   `REPLACE_WITH_SECRET` на тот же секрет из шага 2 → Run.
4. Проверить: `select * from cron.job;` — задание должно появиться, а через
   минуту-две `select * from cron.job_run_details order by start_time desc
   limit 5;` — должны быть успешные запуски (status `succeeded`).

Один игрок, вызванный через `mp-join`/`mp-train` (curl/Postman с его JWT от
anon-входа), должен увидеть, что набор войск завершается сам, даже если он
всё это время не открывал ни игру, ни дашборд — это и есть подтверждение,
что Фаза 2 работает.

Вкладка **«Общий мир»** прямо в самой игре (боковое меню, иконка глобуса) —
уже рабочий тонкий клиент поверх этих трёх функций: вход, ресурсы, набор
войск с реальной проверкой цены/лимита/здания. Полностью изолирована от
одиночной игры (свой код, ничего из `W`/`me()`/`handleAct` не трогает).

## Фаза 5, пятый кусочек — участки 1-3 у ферм/лесопилок/каменоломен/шахт/госпиталя

До сих пор у всех 5 multi-зданий (hospital/farm/lumber/quarry/mine,
`BUILDINGS.*.plots=4` в index.html) строился только участок 0 — не потому,
что остальные три не нужны, а потому что это честно другая работа: участок
0 разблокирован всегда, а участки 1-3 открываются по эпохе ратуши
(`plotUnlocked`/`epochOf`, index.html:2453/2854 — участок 1 с эпохи 2
(ратуша 7 ур.), участок 2 с эпохи 3 (13 ур.), участок 3 с эпохи 4
(19 ур.)). Портированы `epochOf`/`plotUnlocked`/`buildLvAt` в
`_shared/rules.js` и в `mp-build`; `mp-build` теперь принимает `{bk, plot}`
(`plot` только для multi-зданий, по умолчанию 0, вне 0-3 — зажимается в
границы), у каждого участка свой независимый уровень и своя очередь на
постройку — можно вести оба участка сразу в двух бригадах, если оба
разблокированы.

Ничего в `mp-tick`/`_shared/rules.js`'s `production()`/`plotFillCap()` не
пришлось трогать отдельно — они уже суммировали вклад ВСЕХ построенных
участков (Фаза 5, "добыча ресурсов по времени", писалась сразу с расчётом
на несколько участков, просто раньше только участок 0 и мог быть
ненулевым). Панель «Общий мир» показывает все 4 участка каждого
multi-здания отдельными строками ("Ферма — участок 2 — уровень 0"), с
честной пометкой "Участок откроется позже (нужна ратуша N ур.)" для ещё не
разблокированных.

### Как применить

Задеплоить обновлённый **`mp-build`** — принимает новый необязательный
параметр `plot` в теле запроса. `mp-tick`/`mp-join`/`mp-train`/SQL не
трогать.

## Фаза 5, второй кусочек — ратуша и весь HALL_REQ

Первый кусочек (казармы/стрельбище/конюшня/мастерская) разблокировал набор
войск, но сам упирался в потолок: ратуша не поднимается выше 1 уровня без
стены/склада/академии/казарм/госпиталя (HALL_REQ, index.html:2463) на уровне
не ниже текущего уровня ратуши, а без ратуши все здания дальше упираются в
"требуется ратуша N уровня". `mp-build` теперь умеет ещё 5 зданий: **hall**
(ратуша, с проверкой HALL_REQ вместо обычной "требуется ратуша N"), **wall**,
**store**, **academy**, **hospital** (единственное multi среди перенесённых —
BUILDINGS.hospital.plots=4 в index.html — портирован только участок 0, он
один разблокирован всегда и ровно тот, что нужен HALL_REQ; участки 1-3 —
следующий шаг при необходимости). Итого 9 зданий из 15.

По дороге починен баг в `mp-join`: госпиталь заводился скаляром `0` вместо
`[0,0,0,0]` (не учли, что это multi-здание) — новые игроки заводятся
правильно, а `mp-build`/`mp-tick` теперь ещё и самоисцеляют старые записи
задним числом (не падают на них).

Вкладка «Общий мир» в игре показывает и строит все 9 зданий в порядке, в
котором они реально нужны: сначала HALL_REQ-здания, потом ратуша, потом
казармы/мастерские.

## Фаза 4, девятый кусочек — отзыв похода на полпути (mp-recall)

До сих пор поход, однажды отправленный (`mp-attack`), нельзя было ни
отменить, ни развернуть раньше срока — оставалось либо ждать боя, либо
просто закрыть вкладку. Новая Edge Function **`mp-recall`** — зеркало
`recallMarch(m)` (index.html:4770-4780): отряд разворачивается ОТ
ТЕКУЩЕЙ ТОЧКИ на маршруте (линейная интерполяция между домом и целью по
доле пройденного времени — `marchPos(m)` в клиенте делает то же самое
покадрово вдоль настоящего пути), не мгновенно из дома и не от цели —
чем дальше отряд уже прошёл, тем дольше идти обратно, той же формулой
скорости, что и исходный марш.

Работает только для похода в пути (`mode:"attack"`, `state:"go"`) —
уже возвращающийся отзывать нечего (в клиенте `recallMarch` тут просто
молча выходит, но это фоновый вызов без ответа пользователю; здесь это
прямое действие по кнопке, поэтому честнее вернуть ошибку). Изначальное
событие `march_arrive` (на исходное время прибытия) отдельно не
отменяется — просто становится безвредным no-op'ом за счёт уже
существующей защиты `mp-tick` ("уже разобрано/отменено", проверка
`m.state!=="go"`), той же, что защищает от двойной обработки где угодно
ещё; никакой новой логики отмены заводить не пришлось.

Панель «Общий мир»: кнопка «Отозвать» у каждого похода в разделе «Отряды
в поле», видна только пока он ещё идёт (не у уже возвращающихся).

### Как применить

1. Создать новую Edge Function **`mp-recall`** (тело — `supabase/
   functions/mp-recall/index.js`, самодостаточный, копия как у остальных).
2. `mp-tick`/`mp-train`/`mp-build`/`mp-attack`/`mp-heal`/`mp-scout`/
   `mp-join`/SQL не трогать — вся логика самоограничена в новой функции,
   опирается на уже существующую защиту тикера от повторной обработки.

## Фаза 4, восьмой кусочек — разведка чужого города (mp-scout)

Здание «Разведка» (`p.b.scout`) уже строилось и считалось в мощь (Фаза 5,
четвёртый кусочек), но сама механика не существовала — нападать
приходилось вслепую, не зная даже, есть ли у цели хоть один боец. Новая
Edge Function **`mp-scout`** — зеркало `sendScout(p,tx,ty)`/`EV.scouted`
(index.html:4704-4730/4877-4893): лазутчик не занимает слот похода (свой
отдельный лимит одновременных вылазок — `SCOUT_TABLE.scouts`, 1 на
уровнях 1-4, 2 на 5-10, 3 на 11+), бежит заметно быстрее армии
(`SCOUT_SPEED_MULT=2.2`, плюс надбавка от прокачки самого здания —
`SCOUT_TABLE.bonus`), без войск с собой, без боя, и не возвращается домой
— снимает показания на месте и тут же гасит марш (то же самое, что и в
клиенте: "он один и налегке, возвращать домой нечего").

Честные упрощения:
1. Цель — игрок по id, не клетка карты (та же причина, что и у
   `mp-attack` — `map_cells` не сгенерированы в общем мире).
2. Глубина донесения (`scoutSnapshot`, index.html:5237-5282) зависит от
   технологии «Маскировка» (`p.tech.mil_scout2`) — целого дерева
   исследований, которое на сервер ещё не перенесено вообще (самая
   большая оставшаяся задача этого переноса). Честная заглушка — `se=0`
   всегда, то есть донесение несёт РОВНО то, что даёт `se=0` в реальной
   формуле: только общее число войск цели, без разбивки по родам/тирам,
   без запасов, без стены, без полководца — не урезанная имитация, а та
   же формула на минимальном тире.
3. `power(q)` (общая мощь цели) не перенесена — вместо неё в донесении
   просто уровень ратуши, самостоятельный честный показатель силы,
   который уже есть на сервере.

`mp-tick` умеет новый `type:"scout_arrive"` (`applyScoutArrive`) — пишет
письмо (`kind:"scout"`) с составом донесения и сразу удаляет марш
(никакого `march_home`, лазутчик не возвращается). Цель под щитом мира
всё равно разведывается (щит блокирует только атаки, не разведку, как и
в клиенте) — донесение честно помечает `shielded:true`.

Панель «Общий мир»: кнопка «Разведать» у каждого соседа (видна только
если разведка уже построена), новая рубрика «Разведка» с донесениями.

### Как применить

1. Создать новую Edge Function **`mp-scout`** (тело — `supabase/functions/
   mp-scout/index.js`, самодостаточный, копия как у остальных).
2. Задеплоить обновлённый **`mp-tick`** — добавился `case "scout_arrive"`.
3. `mp-train`/`mp-build`/`mp-attack`/`mp-heal`/`mp-join`/SQL не трогать.

## Фаза 4, седьмой кусочек — лечение раненых (mp-heal)

Прямое продолжение прошлого шага: тяжелораненые (`p.wounded`) начали
копиться в бою, но забрать их обратно было неоткуда — новая **`mp-heal`**
закрывает это. Зеркало `startHeal(p,type,tier,n)`/`EV.heal`
(index.html:5795-5809/4867-4873) — та же одна очередь лечения на игрока
(`p.heal`, отдельная от очереди набора `p.train[type]`), тот же
`canPay`/`pay`/`healDuration`. Лечение стоит вдвое дешевле и идёт вдвое
быстрее полного набора того же юнита и никогда не требует золота
(`healUnitCost`/`healUnitTime`, index.html:2840/2844); предел за раз —
`trainCap` от максимального (не суммарного) уровня среди построенных
участков госпиталя, ровно как в клиенте. Только тир 1 — в общем мире
набор войск тоже только тира 1, другим тирам взяться неоткуда.

По пути перенесён и сам `healUnitCost`/`healUnitTime`/`healDuration` в
`_shared/rules.js` — включая честный разбор направления формулы
`healSpeedBonus` (числитель, не `(1+bonus)` в знаменателе, как у
`trainSpeed`/`build` — в index.html эту формулу когда-то дважды чинили в
неверную сторону подряд, тот же разбор перенесён в комментарий).

`mp-tick` умеет новый `type:"heal"` (`applyHeal`) — на завершении раненые
переезжают из `p.wounded` в `p.troops`, `p.heal` очищается; количество
клампится по факту на момент завершения, тот же принцип "текущее
состояние, не снимок", что и у `march_arrive`.

Панель «Общий мир» — новая рубрика «Лазарет» (видна только если есть кого
лечить или лечение уже идёт), с тем же ползунком/кнопкой, что и «Набор
войск». Как и в «Добыча/час», здесь НЕ вызывается настоящий `healUnitCost/
healDuration` из одиночной игры — те читают `bonuses(p)`, а у панели нет
полноценного объекта игрока — вместо них та же лёгкая переформулировка без
бонусов, что и на сервере (`healBonus=1`/`healSpeedBonus=1`).

### Как применить

1. Создать новую Edge Function **`mp-heal`** (тело — `supabase/functions/
   mp-heal/index.js`, самодостаточный, копия как у остальных).
2. Задеплоить обновлённый **`mp-tick`** — добавился `case "heal"`.
3. `mp-train`/`mp-build`/`mp-attack`/`mp-join`/SQL не трогать.

## Фаза 4, шестой кусочек — лазарет защитника в бою

Ещё один явный пробел: госпиталь уже строился (даже все 4 участка, см.
предыдущий шаг ниже по файлу), считался в HALL_REQ и в мощь — но потери в
бою всегда гибли насмерть целиком, лазарет никак не участвовал. В реальном
клиенте (`hospitalSplit`, index.html:4351-4423) это не так: часть потерь
(`SLIGHT_WOUND_FRAC=12%`) отделывается лёгким испугом и НЕМЕДЛЕННО
возвращается в строй в том же бою, ещё часть едет в лазарет (в пределах
его вместимости — `HOSPITAL_CAP_TABLE`, сумма по всем построенным
участкам) и остаётся там как `p.wounded`, и только то, что физически не
влезло в лазарет, гибнет по-настоящему. При штурме ЧУЖОГО города
(`mode:"siege-attack"`) исключений нет — атакующий теряет войска насмерть

## Фаза 4, четвёртый кусочек — стена защитника в бою

Бой (`resolvePvp`/`dmgTo`) раньше вообще не учитывал стену защитника, хотя
уровень стены уже строится (Фаза 5) и участвует в подсчёте мощи — штурмовать
что стену 0, что стену 25 уровня было одинаково больно. Теперь честно
перенесены `tableAt`/`wallDefBonus` (index.html:2895-2911, дословно, вплоть
до дробной интерполяции по уровню) и подключены в `dmgTo` ровно так, как в
`resolveBattle()` (index.html:4142/4208-4209): множитель `defWall = 1 +
wallDefBonus(lv)*(1+bonus)` умножает ИМЕННО дробь `def/70` внутри
смягчения урона (`mitig = 1 + (def/n)/70 * defWall`), а не всё выражение
целиком — важная деталь, легко перепутать. `bonus` (`D.B.wallBonus`, из
`bonuses()`) по заведённой в этом файле традиции временно = 0, как и все
остальные `bonuses()`-члены везде в общем мире.

Стена защищает **только защитника** — как и в клиенте (`dA=dmgTo(A,sa,sd,
wallMul,...)`, но `dD=dmgTo(D,sd,sa,1,...)`): своя стена атакующего его
марширующий отряд не прикрывает. Уровень стены читается из `p.b.wall`
защитника прямо на момент боя (тот же принцип «текущее состояние, не
снимок», что и у самого гарнизона со второго кусочка); отсутствие `p.b`
у совсем старой записи не роняет бой — просто трактуется как стена
уровня 0 (без бонуса).

Форма атаки в панели «Общий мир» больше не пишет «без стены» — стена
теперь настоящая; остаются честно незаконченными только полководцы и
погода (полный `resolveBattle()` — отдельная большая задача).

### Как применить

## Фаза 4, второй кусочек — настоящий марш со временем в пути

Раньше `mp-attack` бил мгновенно (см. первый кусочек ниже) — теперь
заводит настоящий марш: зеркало `sendMarch`/`arriveMarch`/`recallMarch`/

новой SQL/pg_cron-настройки не понадобилось):

1. **`mp-attack`** — списывает отправленную часть гарнизона из дома сразу

   `W.players` по факту прибытия). Если цель пропала или встала под щит —
   бой не случается, отряд просто разворачивается (зеркало `recallMarch`

3. **`mp-tick`**, `type:"march_home"`: выжившие вливаются обратно в
   домашний гарнизон, строка `marches` удаляется.

Панель «Общий мир»: форма атаки честно называет расстояние и то, что
марш/время в пути уже настоящие; новый раздел «Отряды в поле» — список
собственных походов с обратным отсчётом (свои же строки `marches`,

## Фаза 5, четвёртый кусочек — добыча ресурсов по времени

Ресурсы в общем мире теперь **растут сами**, как и обещано в третьем
кусочке — закрывает главный оставшийся пробел. Перенесена "ленивая
экономика" index.html (`syncRes`/`production`/`plotFillCap`, index.html:
3790-3860): ничего не тикает само по себе на сервере (никакого нового
`pg_cron`-задания не понадобилось) — добыча досчитывается по разнице
`now - resAt` при КАЖДОМ обращении к игроку: `mp-join` (в том числе на
каждый опрос — вкладка «Общий мир» дёргает `mp-join` раз в 5с, теперь это
ещё и способ получить свежие ресурсы) и перед `canPay`/`pay` в `mp-train`/
`mp-build`, ровно как в одиночной игре, где та же функция вызывается при
любом чтении/трате, а не тикает по таймеру.

Как и раньше, участки 1-3 у ферм/лесопилок/каменоломен/шахт ещё не
перенесены — добыча считается только с участка 1 (столько же, сколько уже
можно построить, см. третий кусочек). `bonuses(p).prodAll/prodFood/...`
(зависят от рас/генералов/академии) — та же временная заглушка (=0), что и
везде: числа приблизительные, но структурно верные, реальные бонусы
подключатся вместе с полным переносом `bonuses()`.

Важный нюанс, унаследованный из одиночной игры (не баг): добыча за один
"синк" ограничена `plotFillCap` участка — как в RoK, где добыча копится до
"ёмкости" и дальше не растёт, пока не забрать. Если не заходить очень
долго, при возврате начислится не безгранично накопленное, а максимум
вместимости участка (тот же принцип, что в одиночной игре).

Новых Edge Functions нет — изменились существующие: `mp-join` (досчитывает
и сохраняет ресурсы при каждом ответе; у новых игроков `resAt` теперь
верно равен моменту создания, а не 0 — иначе первый же синк решил бы, что
прошли миллиарды секунд с эпохи Unix), `mp-train`/`mp-build` (синк перед
проверкой оплаты). Панель в игре показывает "Добыча/час" рядом с текущими
ресурсами (клиентский превью через уже существующий глобальный `prodRate`,
без вызова полного `bonuses()`, чтобы не тянуть весь игровой объект игрока
ради одной цифры).

### Как применить

## Фаза 5, третий кусочек — ферма/лесопилка/каменоломня/шахта (без добычи)

Добавлены все 4 экономических здания (ещё multi-здания, plots:4 у каждого,

## Фаза 5, первый кусочек — постройки казарм/стрельбища/конюшни/мастерской

Раньше единственные 4 здания, разблокирующие набор войск (barracks/range/
stable/siege), можно было поднять только вручную через SQL — теперь это
делает сама вкладка «Общий мир» в игре. Четвёртая Edge Function:

- **`mp-build`** — зеркало `startBuild` из index.html (ограничено этими 4
  зданиями — ни одно не multi-участок, `HALL_REQ` их не гейтит). Тело:
  `{ bk: "barracks"|"range"|"stable"|"siege" }`. Проверяет: не занята ли
  бригада, не идёт ли уже набор в этом же здании, потолок 25 уровень,
  требуемый уровень ратуши, хватает ли ресурсов — списывает и кладёт
  событие `type:"build"` в `events`.
- **`mp-tick`** обновлён — теперь разбирает и `type:"build"` (зеркало
  `EV.build`), не только `type:"train"`.

`bonuses(p).build`/`buildCostCut` (зависят от рас/генералов/академии) —
та же временная заглушка (1/0), что и `trainSpeed` в Фазе 2, тем же
способом помечена в `_shared/rules.js`. Таблицы `BARRACKS_TABLE`/
`SIEGE_TABLE` — буквальная копия из index.html, сверены тестом на точное
совпадение чисел.

Остальные 11 построек (ратуша, стена, ферма, лесопилка, каменоломня,
шахта, академия, склад, лазарет, дозор, разведка) — следующие шаги,
каждое отдельным переносом.

### Как применить

Те же шаги, что в Фазе 2, плюс:

1. Задеплоить **`mp-build`** — Dashboard → Edge Functions → Create Function
   → имя `mp-build` → код из `functions/mp-build/index.js` целиком
   (самодостаточен, как и остальные три).
2. Передеплоить **`mp-tick`** — код обновился (добавился разбор
   `type:"build"`), нужно заменить содержимое существующей функции на
   актуальное из `functions/mp-tick/index.js`.
3. Ничего в SQL менять не нужно — `0002_phase2_tick.sql` уже накатан,
   pg_cron продолжает дёргать тот же `mp-tick` по тому же расписанию.

Дальше (Фаза 3) — то же самое, но видно всем игрокам сразу, и построек/
действий станет больше.
